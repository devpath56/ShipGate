# Intent profile (Forge, approved)

Generated by Opsera Forge's New Build journey (Intent stage), 2026-09-23. The first draft listed
"Backend API or server-side persistence" and "CRUD beyond seed data" as out of scope; both were
corrected in the Forge chat before approval, so the enforcement engine is backend-owned. This is the
approved version.

## Vision

Replace the inefficient email-and-meeting-based change advisory board process with ShipGate — a modern, deterministic release-governance web application that enforces severity-based blocking policies, provides transparent gate verdicts for every change, and maintains a tamper-evident audit ledger, ensuring that critical security findings can no longer be rubber-stamped as informational.

## Target personas

- **Developer** — submits changes into the governance queue and views gate status, findings, and ledger history.
- **Approver** — reviews changes, approves eligible changes, and ships eligible changes when policy gates allow it.
- **Security Owner** — reviews and resolves security findings; resolving a finding requires a note.
- **Judge / Guest** — uses the application without login to evaluate the demo experience, inspect governance behavior, and switch roles for presentation or judging purposes.

## Core features

1. **Lightweight Backend API & State Transition Engine** (priority 1) — in-memory store seeded on startup; the backend owns all state transitions and gate enforcement; POST /reset restores seed data; every successful and refused transition appends a hash-chained ledger event.
2. **Data Model & Seed Data** (priority 1) — changes, findings, policies, gates, ledger_events; 8 changes CHG-1041 to CHG-1048; CHG-1042 "Add vendor export API" with one CRITICAL secret-handling finding ("live credential detected in generated specification") and two medium findings; policy "Secrets must not ship", high and above, owner Security Owner.
3. **Gate Dashboard** (priority 2) — changes grouped by allow/block verdict with exception counts.
4. **Change Detail Screen** (priority 2) — findings, policy evaluation, gate verdict, ledger timeline with hash-chain integrity.
5. **Role Switcher Demo Control** (priority 2) — Developer / Approver / Security Owner / Judge-Guest; controls permitted actions; not authentication.
6. **Responsive Modern Design** (priority 2) — 375px to 1280px, no horizontal scroll.
7. **Policy List Screen** (priority 3).
8. **Legacy View Mock** (priority 3) — email thread and meeting notes showing CHG-1042 rubber-stamped: "LGTM, approved — findings are informational."

## Technical constraints (excerpt)

- No authentication; the role switcher is a demo control.
- The backend owns all state transitions and policy enforcement; the frontend only calls the API.
- A change with an open finding at or above an active policy's threshold cannot transition to APPROVED or SHIPPED.
- Every successful and every refused transition appends a hash-chained ledger event.

Confidence reported by Forge: 94%.
